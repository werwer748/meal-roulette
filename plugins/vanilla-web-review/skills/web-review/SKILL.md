# 바닐라 웹 코드 리뷰

프레임워크가 없는 코드에는 안전망도 없다. React가 막아주던 XSS, 번들러가 잡아주던 문법 오류,
상태 관리 라이브러리가 강제하던 단방향 흐름이 전부 사람 몫이다. 이 리뷰는 그 빈자리를 메운다.

## 순서

### 1. 기계가 잡을 수 있는 건 먼저 기계에 맡긴다

```bash
./scripts/check.sh        # lint(문법·금지 패턴) → build(단일 파일 제약·용량) → test(순수 로직)
```

검사 스크립트의 위치는 프로젝트마다 다르다. `scripts/check.sh` → `check.sh` → `package.json`의
`test`/`lint` 스크립트 순으로 찾아보고, 아무것도 없으면 이 단계는 건너뛴다(없다는 사실을 보고에 한 줄로 적는다).

기계가 통과시켰다는 전제에서 시작해야 사람이 볼 것 — 논리, 경합, 경계값 — 에 집중할 수 있다.
**실패했다면 먼저 그것부터 보고한다.**

### 2. 변경 범위를 파악한다

`git diff`(또는 `git diff --staged`)가 있으면 그 범위를, 없으면 대상 파일 전체를 읽는다.
변경된 줄만 보지 말고 **그 줄이 속한 함수와 호출하는 쪽까지** 읽는다.
바닐라 코드는 전역 상태를 공유하는 경우가 많아, 지역만 보면 부작용을 놓친다.

### 3. 체크리스트를 순서대로 훑는다

위쪽이 더 치명적이다. 각 항목에서 "이 코드가 깨지는 구체적 입력"을 떠올려 보고,
떠오르지 않으면 지적하지 않는다.

**① 저장소 (localStorage / sessionStorage)**
- 읽기·쓰기가 `try/catch` 안에 있는가 — 시크릿 모드·차단 설정에서 접근만 해도 throw한다.
- `JSON.parse` 결과를 검증하는가 — 손으로 고친 값, 구버전 스키마, `null`이 그대로 상태가 되면 첫 렌더에서 죽는다.
- 저장 실패(용량 초과)를 사용자에게 알리는가, 아니면 조용히 데이터를 잃는가.
- 스키마를 바꿨다면 기존 사용자의 저장값이 어떻게 되는가 (버전 키·마이그레이션).

**② XSS와 DOM 주입**
- `innerHTML`에 사용자 입력이나 저장소에서 온 값이 템플릿 리터럴로 들어가는가 → `textContent`로.
- 구조는 `innerHTML`, 값은 `textContent`로 나누는 패턴이면 통과.
- `insertAdjacentHTML`, `outerHTML`, `document.write`, `new Function`, `eval`, `setTimeout('문자열')`도 같은 눈으로 본다.
- 속성 주입(`href="javascript:"`, `onerror=`)도 확인한다.

**③ 이벤트와 수명주기**
- 목록을 다시 그릴 때마다 리스너를 새로 붙이는가 → 같은 요소에 중복 바인딩되거나, 떼어낸 노드가 남는다.
- 다시 그리는 도중 포커스·입력 중이던 값·스크롤 위치가 날아가는가.
- `transitionend`·`animationend`에만 의존하는가 → 탭이 백그라운드로 가거나 transition이 취소되면 영원히 안 온다. 타임아웃 안전망이 필요하다.
- `ResizeObserver`/`setInterval`/`addEventListener`를 붙였다면 해제 시점이 있는가 (SPA·모달에서 특히).

**④ 애니메이션과 Canvas**
- 애니메이션이 도는 중에 상태가 바뀌면 어떻게 되는가 — 재렌더가 중간 프레임을 덮어써 결과와 화면이 어긋나는 게 전형적인 버그다.
- 연출 중 입력이 잠기는가 (두 번 눌러 두 번 도는 문제).
- Canvas: `devicePixelRatio` 반영, 크기 변경 시 재렌더, `canvas.width` 대입이 내용을 지운다는 점.
- 누적 transform을 쓰는가 — 매번 0도에서 시작하면 되감기는 연출이 된다.
- `prefers-reduced-motion`에서 대체 경로가 있는가.

**⑤ 무작위성**
- `Math.random() % n` 또는 `crypto` 값에 모듈로를 취하는가 → 편향. 거부 샘플링이 필요하다.
- 결과를 먼저 정하고 연출을 역산하는가, 연출이 끝난 자리를 읽어 결과를 정하는가.
  후자는 부동소수점 오차로 화면과 결과가 어긋난다.
- "공정하다"고 적혀 있으면 실제로 균등한지 확률을 계산해 본다.

**⑥ 경계값**
- 항목이 0개 / 1개 / 아주 많을 때 각각 렌더와 로직이 성립하는가.
- 필터를 모두 끄면? 검색 결과가 없으면? 입력이 공백뿐이면? 중복 이름이면?
- 폴백이 무한 루프나 조용한 실패로 빠지지 않는가.

**⑦ 접근성**
- 동적으로 바뀌는 결과에 `aria-live`가 있는가.
- 키보드만으로 전체 흐름이 가능한가 (모달 Esc, 포커스 이동·복귀, `:focus-visible` 유지).
- 아이콘 버튼에 이름이 있는가 (`aria-label`).
- 색만으로 상태를 구분하지 않는가. 텍스트 대비는 충분한가(다크 모드 포함).

**⑧ 반응형과 단일 파일 제약**
- 좁은 화면(390px)에서 가로 스크롤이 생기지 않는가.
- 고정 px 대신 `clamp()`/`%`를 쓰는가.
- 외부 CDN·폰트·이미지를 참조하면 오프라인에서 깨진다 — 단일 파일 프로젝트에서는 결함이다.
- `alert`/`confirm`/`prompt`는 페이지를 멈춰 자동화·훅 검증을 막는다. 인라인 UI로 대체돼 있는가.

## 보고 형식

이 형식을 그대로 쓴다. 사람이 위에서부터 읽으며 바로 고칠 수 있어야 한다.

```markdown
## 리뷰: <대상>

**자동 검사**: lint ✓ / build ✓ / test ✓ (16개)   ← 돌렸다면 결과를 먼저

### 🔴 고치고 커밋해야 함
1. **<한 줄 요약>** — `index.html:123`
   재현: <구체적 입력·조작 → 무슨 일이 일어나는가>
   원인: <왜 그렇게 되는가>
   수정: <무엇을 어떻게>

### 🟡 고치면 좋음
...같은 형식...

### 🟢 참고
- <취향·대안 수준의 메모>

### 확인했고 문제없던 것
- <검토했지만 이상 없던 항목을 짧게 — 리뷰 범위를 보여준다>
```

## 지적의 기준

**🔴는 재현 시나리오를 못 쓰면 🔴가 아니다.** "XSS 위험이 있습니다" 말고
"메뉴 이름에 `<img src=x onerror=alert(1)>`를 넣고 새로고침하면 실행된다"라고 쓴다.
구체적인 입력과 결과를 못 적겠으면 🟡이나 🟢로 내리거나 빼라.

지적 건수를 채우려 하지 마라. 문제가 없으면 없다고 말하는 게 훨씬 쓸모 있다.
반대로 눈에 띄는 리팩터링 기회는 🟢에 한두 줄로 남겨 두면 다음 사람이 고맙다.

코드의 의도를 먼저 읽어라. 이상해 보이는 코드에는 대개 이유가 있다 —
주석과 주변 코드를 보고도 이유를 못 찾았을 때만 지적한다.
